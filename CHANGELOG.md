# Changelog

Versions follow `MAJOR.MINOR.PATCH`. The current version is in `VERSION`.

## 0.17.0 (2026-10-24)
- Phase 7a, the agents' questions in Studio: an agent started from Studio no longer just fails when it wants something its rules do not allow. Claude Code asks TestHive (`--permission-prompt-tool`, served by `scripts/lib/ask.py`, a small MCP server; nothing installed), and the job panel shows the question with the full command or file: **Allow once** or **Deny**, with a note to the agent, signed. No answer in 10 minutes (`TH_ASK_MINUTES`) is a No. Deny rules, the hooks and the blocked commands still apply before any question; agents cannot write the answers (the hook protects `runs/agents/`). Questions and answers are kept in the job's folder and its log.
- Phase 7b, Android exploration from Studio: **Explore the app** in Sources (after uploading the APK) starts the analyst on the Android device you pick from those adb sees; it installs the app (`explore-android.sh ... packages` finds it) and walks its screens. Sources shows the recorded screens and the report.
- New demo `demo/phase7/run.sh` (recorded agents: one asks twice, the person allows and denies; one explores two screens on a stand-in device), in the selftest and CI.
- Roadmap: 3b, 5c, 6b and 8 are not planned (owner decision); the roadmap is complete.

## 0.16.0 (2026-10-24)
- Phase 6a, reporting: one bug register for the project, `reports/bugs.csv` (`bug add | status | list`, or Studio's new **Reports** tab; **Report a bug** on a failed case in the Execution tab fills it in). A person's report links the bug to the failed tests of the open cycle; marking it Fixed asks for their retest. The defect-triage agent writes its bugs there instead of `reports/BUG_REPORT.md`.
- `report <MODULE>`: one self-contained HTML test report of the approved test cycle (opens offline, prints to PDF): TestHive's Go / No-go suggestion with its reasons and the risks to accept, the results, the bugs, the requirements that passed or fail, the pass rate per cycle and per run, small failure screenshots, and the agents' cost per stage. Studio opens it sandboxed.
- The reporting stage: a named person decides Go or No-go with the reason (`report decide`; Go is refused with an open Blocker); the decision goes stale when the bugs or the cycle change; approval freezes the report, the register and the decision in `reporting/baseline/<MODULE>/v<n>/`. Every stage of a module can now be approved.
- New demo `demo/phase6/run.sh`: the phase 5 cycle (its bugs now in the register), then the report (TestHive suggests No-go), a late change that makes it stale, the product owner's Go with the reason, and the sign-off (also in the selftest and CI, where it replaces the phase 5 step).
- `init-project` creates the empty register; the `guard_records` hook protects `reporting/`, `reports/bugs.csv` and the reports (only the scripts write them; the report's checksum is kept in `reporting/<MODULE>/built.json`, and its one script is the only one its CSP allows); `bug add` accepts only cases of the approved design; `cycle fixed` (and Studio's Mark fixed) also marks the register's bug Fixed.

## 0.15.0 (2026-10-24)

BrowserStack mobile: `scripts/lib/browserstack.py` uploads the app and the module's flows, starts the build on the device, waits and writes the results as junit with each flow's video link, so cycles and the gate work as before.

- New demo `demo/phase5b/run.sh`: the same smoke tests on local Edge and on a remote browser, and two flows on a BrowserStack device, with local stand-ins for BrowserStack and made-up keys (also in the selftest and CI). Not checked against the real BrowserStack service yet.

## 0.14.0 (2026-10-24)
- Phase 5a, execution: once the automation is approved, `cycle start <MODULE> "<name>" --env <name>` (or Studio's new **Execution** tab) starts a test cycle on one environment. Every functional case of the approved design gets its result in it: automated cases from the runs on that environment since the cycle started, the others recorded by hand (Passed, Failed with its bug, Blocked with a note), signed.
- Bugs: a failed automated test is linked to its bug (`cycle bug`); a bug marked fixed (`cycle fixed`) makes its cases due for a retest, and `retest web|api <MODULE>` reruns only those (`run-web` and `run-api` take `--ids`). A test that passed and failed with no fix in between is flaky and blocks the cycle until it is fixed or quarantined with a reason (it keeps running).
- The execution stage is approved on the cycle's results (`cycle check --for-approval`), recorded in `execution/baseline/<MODULE>/v<n>/`; the cycle is frozen while it waits for approval and after it.
- Evidence: a failed web test keeps its video (new), screenshot and trace; every API request keeps a text log of the request, the response and its checks, with Authorization, cookies and secret-looking fields masked. Studio opens them from the run.
- Run picker: Studio's Run (Automation tab) picks the environment from the project's `.env.<name>` files (names only); the cycle's runs use the cycle's environment.
- New demo `demo/phase5/run.sh`: build 1.0 of the stand-in app has a planted bug and a flaky resend; the cycle finds both, the tester records the cases run by hand, build 1.0.1 fixes the bug, the failure is retested and the cycle approved (also in the selftest and CI).
- Fixes: the phase 4b token change had not applied (`TEST_API_TOKEN` was still on Newman's command line); the demos no longer copy your `.env.<name>` files into their temporary folder.

## 0.13.0 (2026-10-24)
- Phase 4b, contract tests: with Postman + Newman approved and an OpenAPI spec among the module's sources, `scaffold` (or `contract <MODULE>`) builds `api/collections/<MODULE>.contract.postman_collection.json`, one request per endpoint that checks the status is one the spec lists and the JSON body matches the spec's schema. No agent and no test data: request values come from the spec's examples. The collection remembers the spec's checksum, so a changed spec makes it stale until it is rebuilt. Run it with `run-api <MODULE> --contract` (bearer-protected endpoints get `TEST_API_TOKEN` from `.env`, passed to Newman in a temporary file, not on the command line). Spec paths that are not plain paths are skipped.
- The gate needs the contract tests current and run since they were built; an endpoint that answers differently from the spec blocks approval until it is listed with its bug ID in `api/collections/<MODULE>.contract-bugs.txt`. Studio's Automation tab shows the contract tests, their state and failing endpoints, and runs them (**Contract tests** in the Run list); the next step points to them.
- E2E journeys: the web fixture gains `api` (requests to `API_BASE_URL`), so a journey sets up or checks data through the API inside a Playwright test, with shared steps in `web/pages/<MODULE>/steps.ts`; placeholders of `@e2e` cases say so.
- Demo `demo/phase4`: the contract tests run against the stand-in (they find two responses the spec does not list), a second app instance (`app.py --break-contract`, environment `.env.broken`) shows a wrong field type caught, and TC-SIGNUP-048 is now a web and API journey.
- Fix: the phase 2b check stopped after the project picker check, before its API walkthrough.

## 0.12.0 (2026-10-24)
- Phase 4a, automation: once the tools are approved, `scaffold <MODULE>` (or Studio) sets up the test project for Playwright, Postman + Newman and Maestro with one placeholder test per approved functional case marked Automation Yes. Each placeholder carries the case's steps, expected result, test data and tags and is skipped or fails until it is written; nothing that exists is overwritten; the case sheet's Automation Spec is filled. Case text is written as comments and string literals, never as code.
- The engineers (Run buttons in Studio, or `/th-web`, `/th-api`, `/th-mobile`) replace the placeholders, smoke first, with page objects and a shared fixture for unique test data (`web/fixtures/testhive.ts`; `getByTestId` reads `data-qa`).
- Run by tag: `run-web|run-api|run-mobile <MODULE> --tag smoke|sanity|regression|e2e` (and `TH_TAG` for `stable.sh`). Environments: `TEST_ENV=<name>` loads `.env.<name>` over `.env` (git-ignored).
- The automation stage: `check-automation` lists what is missing; submit and approval need every case written with a real check and stable (3 runs in a row); approval records the tests and their checksums in `automation/baseline/<MODULE>/v<n>/`. Studio's **Automation** tab shows each case's state, runs the tests by type and tag, and shows the last run with its screenshots, videos and logs; **Submit for approval** in Approvals.
- New demo `demo/phase4/run.sh` with a small local stand-in of the demo app: the recorded engineers' smoke tests (7 web, 4 API) run for real against it and are proven stable; `--check` drives Studio too (selftest and CI; CI installs Newman).

## 0.11.0 (2026-10-23)
- Phase 3, tool advice for functional tests: after the design is approved, `tool-advice <MODULE>` (and Studio's new **Tools** tab) groups the functional cases marked for automation into test types (Web UI, API, Android, iOS) and scores the tools for each (Playwright, Selenium, Cypress; Postman + Newman, REST Assured; Maestro, Appium, Espresso, XCUITest) on fit, ready-made TestHive support, upkeep, running on Windows, team skills, evidence and cost. The best total is recommended; a person chooses, with a reason when it is another tool. Weights and the team's languages are set per project (`tools/settings.json`). No agent runs, so it is free.
- The tools stage is real: it cannot be submitted or approved until every test type has a valid choice made on the current design; approval freezes `tools/baseline/<MODULE>/v<n>/`; a later design approval makes the choice stale until it is checked again. Ready for automation now needs all three approvals. Choices move with a module when it is archived and restored.
- Windows only from now on: CI runs the selftest and every demo (with the browser click-throughs) on Windows, and builds only `testhive-studio-windows.exe`; the docs no longer describe macOS or Linux.
- New demo `demo/phase3/run.sh` (also in the selftest and CI).

## 0.10.0 (2026-10-23)
- Phase 2g, Studio on its own for colleagues: a single Studio program per system (`testhive-studio.exe` on Windows, also macOS and Linux) that needs no Python. `python scripts/build-studio.py` builds it with PyInstaller; the `studio-program` GitHub workflow builds and checks all three and attaches them to a `v*` release. Studio opens any project folder (`--project`, the folder it starts in, the last one opened, or an **Open a project** page with recent projects and **Switch project**).
- Review mode: on a PC without Claude Code or Git Bash the Run buttons are off and the command to hand over is shown; documents, answers, reviews, approvals and Excel all work. Studio itself needs no bash (stage rules in `scripts/lib/stage.py`).
- Excel review packs: each workbook keeps a hidden snapshot, so an upload takes only the rows the reviewer changed (a late workbook, or two copies from two reviewers, never undo newer work; a row changed in both places is refused and listed); the Cover tells reviewers to send the file back. New guide [docs/TEAM-GUIDE.md](docs/TEAM-GUIDE.md): who needs what, the program, sharing the project through git, Excel-only reviewers.
- Explore the built product: always shown (it saves a typed address first), says up front when the web tools are missing, fails clearly when the page cannot be opened, shows progress per page and what it found (**Open the report**), and logs in with a test account from `.env` (`TEST_USER`, `TEST_USER_PASSWORD`; never written down, never typed in Studio). A module with only an address runs **Analyse the built product**.
- Easier to use: module details save as you type; forms mark required fields and show errors next to the field; file pickers look and work like links (keyboard too); the project's address is offered for new modules; placeholders are generic.
- Fixes: on Windows a second Studio could share port 8765 and answer the first one's browser with an empty page (each now owns its port); a second Studio on the same project no longer marks the first one's running agent interrupted; stage commands take a lock so two cannot overwrite `workflow/state.json`; switching project clears the old runs; demos and the selftest leave your recent projects alone.
- Security review fixes: Stop and closing Studio end only the agents that window started (never a process number read from a file); job records must match their folder; Explore types the test password only on the start address's own site over https (or local), writes addresses without their query, and never submits password or logout forms while logged in; the program's `--lib` runs only TestHive's own libraries and `--script` only for the recorded agents; network-share paths are refused as project folders; a folder never opened on this PC needs a one-time confirmation; Explore output (`analysis/exploration/`) is no longer committed; the stage lock holds its process number, so a slow command keeps it; a job's records stay in its project after Switch project; an import says how many rows you did not change it left as they are; releases carry a SHA-256 file per program.
